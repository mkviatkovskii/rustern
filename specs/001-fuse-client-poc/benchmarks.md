# Benchmarks: Rustern vs ternfuse

Generated by `scripts/bench.sh` on 2026-11-15: ternfs `55508913`, 32 CPUs, Linux 6.18.58.1-microsoft-standard-WSL2, local cluster. All fio jobs use O_DIRECT; they read the 1 GiB corpus file, except `-file4G` jobs, which read a 4 GiB file; sequential jobs run 10 s (looping over the file), random ones 30 s. `-limit256M` jobs run on fresh mounts: Rustern with `--memory-limit 256MiB`, ternfuse with `GOMEMLIMIT=256MiB` (the Go runtime's soft limit), both mounted fresh side by side. Every fio row is the median of 3 rounds and every metadata row of 5; in each round both clients ran the job back to back, the first client swapping each round. Ranges in parentheses are the lowest and highest per-round Rustern / ternfuse ratio. The host page cache (block services' files, shard databases) was dropped before every timed run (`drop_caches` 3, which also drops dentries and inodes), so each starts cold. Rustern is mounted next to ternfuse (same path depth). Targets are recorded, not gated (spec: Performance Targets).

### Block connection pool and directory cache (2026-11-14)

The first run had Rustern at 0.66-0.89x ternfuse throughput, with a block fetch costing
527 µs at p50: 124 µs of TCP connect and 367 µs waiting for the response header, most of
it the block service setting up each new connection. Reusing connections
(`blocks::Conns`) cut a fetch to 182 µs and the connections opened from one per fetch
(110,538 in 15 s) to 16. Directory handles now ask the kernel to cache listings
(cache-dir + keep-cache), as ternfuse does; uncached listings are measured as
`readdir-changed`. ternfuse's single-reader throughput varies between runs (1,510 to
1,832 MiB/s); Rustern's held at 1,875 to 1,886 MiB/s.

### Metrics memory leak (2026-11-14)

Runs before this one showed Rustern's start RSS climbing through the suite (9 to 182 MiB,
peak 258 MiB) and its throughput falling in the later rows. On a fresh mount, one
sequential reader at a steady 1,820 MiB/s grew RSS linearly by 0.41 MiB/s (8.6 to
35.6 MiB in 65 s, about 37 bytes per block fetch). The cause:
`PrometheusBuilder::build_recorder()` does not spawn the exporter's upkeep task, so every
histogram sample stayed buffered until a SIGUSR1 render. `main.rs` now calls
`run_upkeep()` every 5 s. The same 60 s test now holds at 14-16 MiB. In the first run
with the fix, start RSS ended the suite at 57 MiB (was 182) and the peak was 65 MiB (was
258). The rest of the climb is buffers and connections that later workloads with more
readers keep.

### IDE indexing and pool order (2026-11-14)

The first multi-round runs showed Rustern aging: start RSS climbing to 100 MiB and
one-reader throughput falling from 1,678 MiB/s (round 1) to 1,398-1,454 (rounds 2-3).
Two causes:

- The IDE (RustRover's WSL agent, `ijent`) indexed every mount under `ternfs/mnt/`, the
  reference ternfuse included: 12,081 opens, 11,697 reads and 57,843 lookups in 20 s on an
  otherwise idle mount. `ternfs/mnt` is now excluded in the IDE, which leaves its file
  watcher at about 25 ops/s (listings and lookups, no opens). A mount outside the project
  sees no foreign ops.
- Both pools (read buffers, block connections) were FIFO `crossbeam-queue` queues. After
  a 16-reader burst a lone reader cycled through every idle buffer (about 30 MiB, more
  than the CPU cache) and lost 8% (1,760 to 1,620 MiB/s on one mount). Both are now last
  in, first out; the loss after a burst is about 2%, and in the tables above Rustern's
  one-reader rounds are 1,630 / 1,617 / 1,623 MiB/s with no trend. The connection pool's
  order made no measurable difference on loopback; it matters on a real network, where an
  idle TCP connection restarts slow start. Read buffers then moved to `deadpool` (LIFO
  mode) and connections to plain per-address stacks in the `dashmap`; a single-reader
  check after the switch: fresh 1,734 / 1,794 / 1,769 MiB/s, after a burst 1,762 / 1,732 /
  1,758 MiB/s.

The script now keeps per-round rows in `target/bench-results.jsonl`.

| RSS max, MiB | 63 | 159 | 73 | 154 |

A 2 MiB request lifts one reader by 43% at 22% less CPU per GiB: a psync reader waits
one round trip per request, and a 2 MiB request fetches twice the pages in parallel. With

### Buffered reads and readahead (2026-11-14)

Page-cache (not O_DIRECT) sequential reads of the 4 GiB file, one pass per run (no

At the default readahead Rustern matches ternfuse with one reader and is 1.67x with 16.
Raising readahead doubles one reader for both, but Rustern then trails ternfuse (0.85x),

`add` time is undone by the INIT reply); a post-mount root step is the deterministic way.

### Span boundary stalls and next-span warming (2026-11-15, T126)

Where the single-reader time went (cold, 2 MiB readahead, 1 GiB file, per-request trace):
the kernel sends 1 MiB READs in pairs, about 0.8 ms per pair, except at each new span,
where one request waits about 17 ms. 51 such stalls took 451 ms of an 809 ms read. With
the host page cache warm (block files cached) Rustern reads 3.3-3.4 GB/s against
ternfuse's 2.3-2.4, so the client path is not the limit.

Cause, on the block service (`ternfs/go/ternblocks/ternblocks.go`, `sendFetchBlock`):
each fetch opens, stats and sendfiles the block file; for HDD-class storage it calls
`fadvise(SEQUENTIAL|WILLNEED)` from the fetch offset to the end of the block, so the
first fetch of a block starts the disk read of the whole block, and the reader waits for
it. The corpus files are RS 10+4 on HDD-class directories with spans of about 27 MiB
(2.7 MiB per data block), so every span boundary pays that start-up once per data
block. ternfuse (`readRs` in `ternfs/go/client/span.go`) fetches the same way and pays
the same stalls; both clients fetch nothing ahead of the reader.

Fix (client only, no server change): when a read is sequential (within 8 MiB of the
previous read's end on the handle), Rustern fetches the first page of each data block
of the next span (the first readable mirror for a mirrored span) in the background,
once per span (`rustern_span_warms_total`). That one-page fetch triggers the block
service's whole-block WILLNEED a span early, so the disk read overlaps the current span.
After it, the trace shows 2 stalls (40 of 422 ms).

Same method as above (page cache, one pass of the 4 GiB file, caches dropped, 3 rounds
rotated across the three mounts, idle cluster), median MiB/s (range):

| workload | client | readahead 128 KiB | readahead 2 MiB |
|---|---|---|---|
| 1 reader, bs=1M | ternfuse | 716 (662-729) | 1,657 (1,623-1,675) |
| 1 reader, bs=1M | Rustern, no warming | 747 (673-752) | 1,447 (1,413-1,475) |
| 1 reader, bs=1M | Rustern | 1,160 (1,130-1,325) | 2,720 (2,649-3,061) |
| 16 readers, 256 MiB each | ternfuse | 2,003 (1,920-2,028) | 2,165 (2,149-2,166) |
| 16 readers, 256 MiB each | Rustern, no warming | 3,346 (3,277-3,371) | 2,601 (2,432-2,653) |
| 16 readers, 256 MiB each | Rustern | 3,700 (3,660-3,710) | 3,786 (3,693-3,905) |

### Memory (2026-11-14)

Mounted fresh, ternfuse idles at 97 MiB and Rustern at 9 MiB. The `-limit256M` row is
the like-for-like comparison: both fresh, both limited to 256 MiB, 16 readers. There,
Rustern peaks at 53 MiB against ternfuse's 261 MiB (0.20x) and is 1.41x faster, using
0.89 against 1.85 CPU s/GiB. The limit costs Rustern nothing measurable (8,926 against
8,807 MiB/s unlimited).

In the other rows Rustern's peak is 10-16% of ternfuse's, at most 103 MiB, under the
default `--memory-limit`. A peak there is the highest of three rounds, and Rustern keeps
its idle buffers and connections from earlier workloads, so later rounds start where the
busiest workload left off. Growth within a round (`VmHWM` minus the round's start) shows
the per-workload cost: Rustern grows 6-15 MiB in a workload's first round, while its pool
fills, and 0-6 MiB in later rounds; ternfuse grows 94-121 MiB for one sequential reader,
143-353 MiB for 16 and 435-447 MiB for random 128 KiB reads, round after round. ternfuse at
<ref-mount> is long-lived, so its start (428-841 MiB) includes heap the Go runtime kept.

### Metadata latency (2026-11-14)

A single round of the metadata rows was noisy (cold-lookup p99 0.83x in one run, 1.32x in
the next), so the script now runs 5 rounds alternating between clients, each with 10,000
lookups and stats, 200 cached and 20 changed listings, and reports the median with the
range of the per-round ratio. The ranges are tight: cold-lookup p50 0.92-0.98x, readdir
1.00-1.12x, readdir-changed 0.41-0.44x. A p99 range can be wide because the p99 of one
round of 20 changed listings is a single sample. One outlier: in the tables' round 1,
ternfuse answered more than half of its "cold" lookups from the kernel cache (p50
0.74 µs against 184-187 µs in the other four rounds), which puts 236x at the top of the
cold-lookup p50 range; the median is unaffected. The cause is not known; a listing of
`corpus/big` by the IDE's watcher between the cache drop and the run would do it.

Both clients send the same shard requests: a lookup is LOOKUP then STAT_FILE, and an
opendir is one STAT_DIRECTORY, after which the kernel serves the cached listing. `stat` of
a looked-up file never reaches the daemon (no shard request is made). The 0.05 µs
difference earlier runs showed (1.13-1.16x in every round) was the kernel's path walk:
`meta_latency` stats `<mount>/corpus/sizes/size_4096`, and the bench mounted Rustern under
the scratch directory (`/tmp/.../scratchpad/bmnt`, 6 components) while ternfuse is at
`ternfs/mnt/fuse_loc1/mnt` (4, relative to the repository). Over 3 alternating rounds of
10,000 stats, ternfuse took 0.38 µs at p50, Rustern mounted at the same depth
0.37-0.38 µs, and Rustern at the scratch path 0.44-0.45 µs. The script now mounts Rustern
next to ternfuse, and `stat` is 1.00x.

### 4 GiB file (2026-11-14)

`-file4G` jobs read `bench/size_4294967296` (created through ternfuse by the script).
With 16 readers Rustern is 1.15-1.21x ahead, at about half the CPU per GiB. The
one-reader row (0.97x, 0.94-1.04x by round; 0.83-1.01x over earlier single-round runs) is
run-to-run noise, not a property of the file: both files have the same layout (RS(10,4), 184 KiB cells, 28 MB
spans), Rustern fetches each file's spans once, and both clients fetch every byte from the
block services (loopback traffic 1.01x the bytes read; ternfuse's page-cache store does
not serve O_DIRECT reads). Three alternating 10 s rounds per file gave Rustern / ternfuse
1.03 / 0.92 / 0.95 on the 1 GiB file and 1.00 / 1.04 / 0.98 on the 4 GiB file; both
clients read 1,780-1,930 MiB/s with one reader. Its RSS grows by under 1 MiB with either
reader count, at a 52 MiB peak.

### Cluster load after a restart (2026-11-14)

After the host restarted, the local cluster's 256 shards kept writing about 9 KiB/s each
(2.2 MB/s in total) and the disk stayed at about 70% I/O pressure (`/proc/pressure/io`)
for as long as it was watched (over 20 minutes); it is the cluster's idle state on this
WSL disk, not a transient. A bench run made during the first minutes after the restart had
every Rustern metadata row slow (`stat` 2.5x at p50); the next runs, under the same steady
load, did not, and the tables above come from one of them.
